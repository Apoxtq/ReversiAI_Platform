# 开发工作流程（每次提交必须遵守）

---

## 🎓 英国大学毕业设计学术规范

**重要提醒**: 本项目的开发过程须符合**University of Liverpool**的学术标准和**BCS项目准则**。

### 📜 学术开发规范

#### 1. 编码前学术准备
- **文献调研**: 开发前查阅相关算法和工程文献
- **设计论证**: 为技术选型提供充分的学术依据
- **风险评估**: 基于学术经验评估技术风险
- **替代方案**: 准备技术难题的学术解决方案

#### 2. 编码中学术实践
- **注释标准**: 每个函数包含算法复杂度分析和参考文献
- **测试设计**: 基于统计方法设计有意义的测试用例
- **性能度量**: 使用学术标准的性能评估方法
- **错误处理**: 基于软件工程最佳实践设计异常处理

#### 3. 编码后学术验证
- **正确性证明**: 通过测试验证算法实现的正确性
- **性能分析**: 使用标准基准测试评估性能表现
- **文档更新**: 实时更新技术文档和设计决策记录
- **同行评审**: 模拟学术同行评审过程的质量检查

#### 4. 学术道德要求
- **诚信编码**: 禁止任何形式的代码抄袭或不当借用
- **透明记录**: 详细记录所有问题解决过程和决策理由
- **知识分享**: 主动记录可供学术界借鉴的经验教训
- **持续学习**: 开发过程中不断学习和应用新的学术知识

## 编码前
1. 必须先阅读相关模块的接口定义
2. 使用@符号引用现有代码模式
3. 说明本次修改对其他模块的影响
4. 检查.cursor/rules/相关约束
5. 如果修改接口，必须更新依赖模块

## 编码时
1. 每次只修改1-3个相关文件
2. 添加Doxygen格式的注释
3. 使用现代C++特性：智能指针、RAII、constexpr
4. 遵循命名规范和架构约束
5. 实时编译检查（禁止积累错误）

## 编码后
1. 运行 `cmake --build build && ctest` （如果有测试）
2. 检查编译警告（零容忍）
3. 更新相关文档（如果接口变化）
4. 运行基本功能测试

## 不允许的操作
- 不得修改已经稳定的核心接口
- 不得引入未在项目计划中声明的第三方库
- 不得使用裸指针（除非性能关键且已注释说明）
- 不得跳过单元测试直接提交
- 不得在主分支上直接修改（必须通过PR）

## Git提交规范
- 提交信息格式：`[模块] 功能描述`
- 示例：`[AI] Add Minimax algorithm with alpha-beta pruning`
- 每次提交只包含一个逻辑功能
- 提交前必须通过编译检查

## 代码审查清单
- [ ] 架构约束检查通过
- [ ] 单元测试覆盖相关功能
- [ ] 编译无警告
- [ ] 代码风格符合规范
- [ ] 文档已更新
- [ ] 性能测试通过
