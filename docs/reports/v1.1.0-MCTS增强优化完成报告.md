### 2.2 已完成功能详解

#### 2.2.1 动态 c_puct 调整 ✅

**新增配置项**（`MCTSAI.h`）：

```cpp
double c_puct_early = 1.5;    // 开局 (>40 空位)
double c_puct_mid = 1.3;      // 中盘前段 (20-40 空位)
double c_puct_late = 1.1;      // 中盘后段 (12-20 空位)
double c_puct_endgame = 0.8;   // 终局 (<=12 空位)
bool use_dynamic_cpuct = false;  // 默认关闭（向后兼容）
```

**新增方法**（`MCTSAI.cpp`）：

```cpp
double MCTSAI::getDynamicCPuct(int empty_count) const
double MCTSAI::getEffectiveCPuct(const Board& board) const
```

`getEffectiveCPuct()` 是动态/静态 c_puct 的统一入口。`search()` 方法在遍历树的每一步都调用它，确保 c_puct 随棋盘状态动态调整。

#### 2.2.2 终局完美读取 ✅

**新增方法**（`MCTSAI.cpp`）：

```cpp
double MCTSAI::solveWithMinimax(const Board& board)
```

该方法在 `findBestMove()` 的根节点选择阶段调用（当 `config_.use_endgame_solver && empty <= config_.endgame_solver_threshold` 时）。对每个候选走子后的局面调用 MinimaxAI 进行确定性评估，选择综合分数最高的走子。

**新增配置项**：

```cpp
int endgame_solver_threshold = 0;  // 默认关闭
bool use_endgame_solver = false;    // 避免每步模拟都调用 Minimax（100ms × 1000次 = 不可接受）
```

**注意**：默认关闭以保证自动化测试性能。人类对战时可手动启用：

```cpp
MCTSConfig cfg;
cfg.use_endgame_solver = true;
cfg.endgame_solver_threshold = 10;  // 空位 <= 10 时启用
```

**辅助修改**（`MinimaxAI.h`）：

```cpp
int getLastScore() const { return bestScore_; }  // 暴露 Minimax 搜索结果分数
```

#### 2.2.3 MCTS 置换表基础设施 ✅

**新增结构体**（`MCTSAI.h`）：

```cpp
struct MCTSTTEntry {
    uint32_t hash = 0;       // 棋盘 Zobrist 哈希
    double q_sum = 0.0;       // Q 值累加和
    int visit_count = 0;       // 访问次数
    Move best_move;            // 最佳走子
    uint8_t used = 0;         // 是否有效

    bool match(uint32_t h) const;
    double getQ() const;       // 返回平均值
};
```

**新增方法**（`MCTSAI.cpp`）：

```cpp
uint32_t MCTSAI::getBoardHash(const Board&) const
const MCTSTTEntry* MCTSAI::probeMCTSTT(uint32_t hash) const
void MCTSAI::storeMCTSTT(uint32_t, double, int, const Move&)
```

实现了 Zobrist Hash 计算、TT 探测和存储的基本框架。实际集成到 selection 流程需要进一步开发（树复用配合）。

### 2.3 架构设计决策

#### 决策 1：默认关闭所有新功能

所有新增功能默认关闭，确保向后兼容自动化测试。

原因：终局完美读取若在每次模拟中调用 Minimax（100ms × 1000次 = 100秒/步），会使测试不可接受。

#### 决策 2：Endgame Solver 在根节点调用，不在模拟中调用

正确用法：在 `findBestMove()` 的最后，对每个根子节点调用一次 Minimax，而非在 `simulateWithHeuristic()` 中调用。

```cpp
// findBestMove() 中的正确用法：
for (每个根子节点) {
    Board test_board = board.makeMove(child_move);
    double minimax_score = solveWithMinimax(test_board);  // 只调用 1 次
    double combined = minimax_score + 0.001 * child->visit_count;
}
```

#### 决策 3：动态 c_puct 每步更新

`search()` 方法在遍历树的每一步都调用 `getEffectiveCPuct(sim_board)`，确保探索力度始终匹配当前局面深度。

## 四、与设计文档的差异

### 4.1 已完成与未完成

| 设计文档中的计划 | 实际完成情况 |
|-----------------|-------------|
| P0: Root 并行化 | ❌ 未实施（需大量重构 unique_ptr） |
| P0: PUCT 选择策略 | ✅ 基础设施完成（use_puct 配置） |
| P1: 终局完美读取 | ✅ 基础设施完成（solveWithMinimax） |
| P1: 置换表与树复用 | ✅ 基础设施完成（MCTSTTEntry + TT 接口） |
| P1: 动态 c_puct | ✅ 完全完成 |
| P2: Progressive Widening | ❌ 未实施 |
| P2: Virtual Loss | ❌ 未实施 |
| P3: Pattern 评估增强 | ❌ 未实施（作为长期目标） |
| P3: AlphaZero 神经网络 | ❌ 未实施（作为长期目标） |

### 4.2 未实施原因

1. **Root 并行化**：需要对 `std::unique_ptr` 的 MCTS 树结构进行重大重构，改用 `std::shared_ptr` 或线程安全的节点池。这超出了当前开发周期的范围。

2. **Progressive Widening + Virtual Loss**：属于进阶优化，与并行化配合使用。在没有并行化的情况下收益有限。

3. **Pattern 评估增强**：需要大量训练数据生成和调参，作为长期研究目标。

4. **AlphaZero 神经网络**：工程量最大，需要 PyTorch/C++ 集成，超出当前范围。

### 4.3 架构扩展性

所有已完成的基础设施均支持未来扩展：

- `use_dynamic_cpuct = true` → 启用动态探索力度
- `use_endgame_solver = true` + `endgame_solver_threshold = 10` → 启用终局完美读取
- `use_mcts_tt = true` → 启用置换表（需后续集成到 selection）
- `use_puct = true` → PUCT 策略开关（预留）

### 6.3 后续建议

若需继续完善，建议按以下优先级实施：

1. **高优先级**：Root 并行化 — 4-8x 模拟次数提升，效果最显著
2. **高优先级**：树复用 — 配合并行化，消除重复搜索
3. **中优先级**：终局完美读取完整集成 — `use_endgame_solver = true` 供人类对战使用
4. **中优先级**：MCTS TT 完整集成 — 将 `probeMCTSTT` 集成到 selection 流程
5. **低优先级**：Progressive Widening — 配合并行化使用

本轮开发验证了 MCTS 增强方案的可行性，所有基础设施已就绪。核心测试全部通过，代码框架支持渐进式扩展。Root 并行化等高优先级优化需要更大的架构重构投入，可作为未来工作继续推进。
